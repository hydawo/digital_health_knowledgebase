Knowledge Base Architecture

How the agents divide the work, and how the library itself is laid out. The library is a set of plain text files and PDFs in one public GitHub repository. There is no database server. Every change is a commit, so the full history of every claim can be traced.

Part 1

🤖 How the agents work together

Read top to bottom. Hassan sets the questions. The coordinator hands out the work and checks it. Nothing reaches the library without a check, and the reviewer's findings come back to Hassan before anything changes.

Person Coordinator Research agents Independent review (dashed) Outside sources
Why each agent owns its own filesAgents run at the same time. Giving each one a separate set of files means two agents never overwrite each other's edits.
How the scout's work is checkedEach weekly run goes to the coordinator first. A script compares every new paper with Crossref and prints its funding and conflict statements, so the sponsorship label can be checked before the merge.
Why the scout only shortlists studiesA paper's abstract is enough to file it under a device. What happened in a study has to be read from the full paper, so a person-led session writes those up.
Why the reviewer can't editIts findings go to Hassan first. A correction only enters the library after someone has looked at it.

📇 Vendor fact records

A second set of agents keeps the facts a study team decides on, like research programs, prices, data terms and compliance. They run once per company to build its record. After that, a check runs every Monday and one agent fixes whatever it flags.

Agents Fact record Scheduled job and its issue Outside sources
Why two researchers work apartA fact that one of them misses or misreads shows up as a disagreement. The judge then opens the page and settles it, or keeps both sources as a conflict.
Why every fact keeps its quoteThe weekly check can only spot a stale fact if it knows the exact words to look for. A quote that is 90% the same counts as reworded. Anything less counts as missing.
What the weekly check never doesIt never changes a fact. It reports, and the fact keeper reads the page and makes the change. A page that blocks automated visits is never treated as dead. After two weeks it is marked for a check by hand.
Who opens the issueThe scheduled job opens it in this repository, or adds a comment to the one already open. No agent writes it.
Part 2

📚 How the library is laid out

Four modules sit side by side, each with its own write-ups, a comparison table, a source list and a folder of papers. The fifth, measurement science, runs underneath them: one catalogue per domain plus a generated hub page that links back into the other four. A shared folder holds what applies to all five. A script turns the whole thing into the web pages. The vendor fact records sit in their own folder, described below the diagram.

Write-upsOne file per device, platform or study. Every one uses the same headings in the same order, so any two can be compared line by line.
Comparison tablesThe same facts across every device or platform at once, so a reader can scan one column, like cost or raw data access.
Paper ledgersMachine-readable lists of every paper already seen or rejected. They stop the Monday scout from adding the same paper twice.
Confidence labelsClaims are marked Verified, Corroborated, Reported or Unclear, depending on how strong the source is.
Domain hubs (Module 5)One generated page per domain. It lists the domain's own catalogue, then every device profile, paper and study elsewhere in the library tagged with that domain, so a paper never needs two homes.

📇 Vendor fact records

facts/One record per company, 35 in all. Each fact holds the page it came from, the exact words that back it, the date it was read, a confidence label and a date to check it again.
facts/_generated/Tables built from the records by a script. Never edited by hand. A check on every push fails if they no longer match the records.
facts/_drafts/Working files from the baseline run, one folder per company. Each researcher's draft, the gap hunter's findings and the judge's reasoning are kept here.
facts/_reports/One report per weekly check, named by its date. It lists quotes that went missing or changed, pages that changed, dead links and re-checks that are overdue.
tools/facts/The scripts and instructions. A validator that enforces the record rules, the weekly check, the generator that builds the tables, a quote checker, and the written instructions for each baseline agent in prompts/.
Part 3

📜 Each agent's rules

Every agent works from written instructions. The full rule sets are kept in the repository, in shared/agents.md, so they can be read and changed like any other file.

Rules every agent follows
  • Primary sources first: vendor docs, code, FDA records and the papers themselves.
  • Every claim gets a confidence label. A company's claim about itself is never more than "Corroborated".
  • When sources disagree, record both.
  • Every fact must come from a source read that day, never from memory or a file name.
  • Every vendor fact carries the exact words from its source page and the date it was read.
  • No accounts, sign-ins, forms or getting past bot checks.
  • Nothing is posted on GitHub without Hassan's approval.

🔬 Fact researchers A and B

Job
Each fills one company's fact record from scratch, apart from the other. A starts from developer docs, terms and the FDA database. B starts from research, pricing and partner pages. Both then cover every field.
Can change
Only its own draft, facts/_drafts/<company>/A.yaml or B.yaml.
Never
Reading the other draft, the current record or the company's write-up. Using a quote it has not checked on the page.
Rules in
tools/facts/prompts/researcher.md

🕳️ Gap hunter

Job
Looks for what both researchers would miss, in changelogs, deprecation notices, developer forums, FDA and recall databases, partner pages and papers. Then compares what it found with the library.
Can change
Only its findings file, gaps.md, in the company's drafts folder.
Never
Editing the record, the write-up or the tables.
Rules in
tools/facts/prompts/gap-hunter.md

⚖️ Judge

Job
Merges both drafts and the gap hunter's findings into the company's record. Where the drafts disagree, it opens the sources and decides, or records a conflict. It checks every quote on its page again and lists the write-up and table lines the record contradicts.
Can change
The company's record and its own notes on how it decided, judgement.md.
Never
Picking a side without reading the page. Editing the write-up or the tables.
Rules in
tools/facts/prompts/judge.md

✏️ Profile corrector

Job
Brings one company's write-up into line with its record, after checking each of the judge's claims against the record. Adds the generated facts block. Lists the table lines that need the same fix, and one agent per module then applies them.
Can change
That one write-up.
Never
The tables, READMEs, other write-ups, the record or the judge's notes.
Rules in
tools/facts/prompts/profile-corrector.md

📌 Fact keeper

Job
Works the weekly check's issue. Re-reads every flagged page, updates the fact with a fresh quote and date, fixes any write-up the change contradicts, logs it and closes the issue.
Can change
The fact records, the write-ups where a fact changed, and the generated tables, only by running the generator.
Never
A quote typed from memory. A company's own compliance claim marked higher than Corroborated.
Rules in
facts/README.md
